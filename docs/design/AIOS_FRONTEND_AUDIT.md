# AIOS 前端功能审计 —— 保留 / 静默 / 新增

> 2026-07-27 · 基于 AIOS 定位（员工全是 AI 的公司操作系统）
> 原则：**用户是老板，不是操作员。老板的动作只有四个：定目标、做审批、看状态、查结果。**
> 凡是"操作员手工配置"的页面，都是前 Agent 时代的遗产。

## 0. 审判框架

每个现有页面回答三个问题：

1. **谁在用这个功能——老板还是员工？**
   员工（agent）自己就能做的，页面就是多余的。
2. **这是高频决策点还是低频配置点？**
   低频配置（一次设置终身有效）不配占一级导航。
3. **它展示的是状态还是机制？**
   机制（怎么实现）是员工的事；状态（进展如何）才是老板的事。

## 1. 现状：20 个页面的审判结果

### A 类：升级为一等公民（6 个 → 重组为 7 个）

| 现有 | 处置 | AIOS 形态 |
|---|---|---|
| `app/page.tsx`（对话首页） | **降级** | 不再是首页。变成员工 Profile 里的"联系 TA"——聊天是沟通方式，不是产品 |
| `tasks` | **重组** | 工单中心：按员工分组的工作队列（谁在干什么/卡在哪），不是独立任务列表 |
| `knowledge` + `wiki` + `memory` | **三合一直** | 知识资产：员工产出的文档/SOP/决策记录，组织共享。memory 页（个人记忆管理）本身就是机制——老板不该手改 agent 记忆，只该看"TA 学了什么"（进成长轨迹） |
| `cluster` | **升级** | 项目组（AI 群）：多 agent 自讨论、用户旁观。现有 DAG 复核可视化是底子 |
| `security`（548 行） | **拆分** | 审批功能升级为一等公民（审批中心）；权限规则并入内核页——"谁被拦了"比"规则长什么样"重要 |
| `evolution` | **并入** | 员工成长：技能晋升/SOP 蒸馏是"员工升职加薪"，进员工 Profile + 审批源（蒸馏要审批已有红线） |

新的一级导航（7 + 1）：

```
驾驶舱 · 员工 · 目标 · 审批 · 知识 · 活动 · 内核 · 设置(深层)
```

### B 类：静默执行（7 个页面删除，能力保留）

| 页面 | 为什么砍 | 静默后谁接管 |
|---|---|---|
| `cron`（299 行） | 定时任务是"员工的日程"。老板不会帮秘书排日程——告诉小秘"每周五发周报"，cron 表达式 TA 自己写 | Secretary/调度 agent 自建自管；用户只在活动流看到执行记录 |
| `context` | 上下文项是 loop 内部机制（injection_tier/pack 预算是自动化卖点），手工管理等于承认自动化失败 | context manager 自治；用户零感知 |
| `tools`（693 行） | tool pack 动态装载是一号卖点——自动的。手工勾选工具 = 操作员思维 | 工具出现在**员工能力档案**里（编制视角），不再是工具仓库视角 |
| `skills`（556 行） | 技能的终局是员工自己学（evolution 蒸馏）。手工安装退化为"技能市场"浏览 | 大部静默；保留只读市场 + 员工已掌握技能展示 |
| `config`（122 行） | agent 行为参数（阈值/轮次/预算）——evolution 已经在自动调 | agent 自调；极少数进设置深层 |
| `profiles` | 多 profile 是调试期概念。AIOS 用户只有一家公司 | 静默；单一 workspace |
| `login` / `profile` | 单机产品，认证应该无感 | 静默；仅非 loopback 部署时显形 |

### C 类：降级合并（4 个）

| 页面 | 处置 |
|---|---|
| `workflows`（824 行 DAG 编辑器） | **深度思考**：手工编排 DAG 是"人替 agent 做规划"——前 Agent 时代产物。Agent 时代是"目标 → agent 自动规划"。降级为项目组的**高级模板**（可复用流程），从一级导航消失。但注意：DAG 可视化本身有价值（集群 plan 展示），保留渲染、弱化编辑 |
| `devices`（538 行） | 设备节点 = 公司的"分公司/机房"。基础设施层，并入内核页 tab（节点状态）+ 设置（接入配置） |
| `mcp`（323 行） | MCP = 工具供应链。一次接入终身使用，进设置深层。但"员工申请新 MCP"应该走审批流（新能力上岗） |
| `channels`（481 行） | **重新定位**：不是"渠道配置"，是**公司对外窗口**——飞书消息进来路由到具体员工（小秘分拣），外发走员工身份。配置进设置，消息路由规则留一层薄 UI |

### D 类：settings（1407 行巨石）特别处置

按"老板偏好 / 公司制度 / 机房"三层拆：

| 层 | 内容 | 归宿 |
|---|---|---|
| 老板偏好 | 主题/语言/通知方式/模型选择 | 设置（保留，瘦到 ~200 行） |
| 公司制度 | 审批规则、预算总额、能力授予策略 | 并入内核页"治理"tab |
| 机房 | MCP/设备/渠道/执行后端 | 设置深层二级页，平时不可见 |

**关键判断**：settings 里 60% 的 agent 行为参数应该**静默**——
agent 自调（evolution 已在做阈值），用户只在审批里否决。

## 2. 新增：AIOS 必需但不存在的（7 个）

| # | 功能 | 为什么必需 | 后端现状 |
|---|---|---|---|
| 1 | **驾驶舱 Dashboard** | "他们一直在工作"的第一感知。AIOS 的灵魂页面 | 数据全有（kernel events/inbox/预算），缺聚合 API |
| 2 | **员工花名册 + Profile** | New Chat → New Employee。员工是唯一一等资源 | identity registry 已有；缺前端 CRUD + 记忆/成长可视化 |
| 3 | **审批中心** | 用户的主战场。三态：决策/权限/高危 | escalation + inbox + mediate 三个源，缺**统一审批队列 API** |
| 4 | **目标管理（O/KR）** | Goal-driven 是 Agent 与 Task 工具的本质区别。目标自动分解为工单是核心叙事 | goal_mode 是单 session 级；缺组织级 O/KR 数据模型（新表） |
| 5 | **成本中心** | AI 公司的财务室：token/成本按员工/项目/目标三维度。金算的视图 | charge_tokens 已逐进程记账，缺聚合投影 |
| 6 | **招聘向导** | 创建员工 = 角色→能力→预算→记忆初始化。AIOS 的"入职流程" | identity.create 已有，缺向导 UX |
| 7 | **值班室（实时态势）** | 员工实时画面聚合（desktop shots/cluster 状态/进程 CPU-token 速率）。"看一眼机房" | /api/desktop/shots + kernel process 已有，缺聚合 |

候选第 8：**审批收件箱**（请示/汇报分离的通知中心）——
现有"通知"是系统事件，AIOS 的通知应该是"员工请示"（可行动）与"员工汇报"（已发生）两类，请示直达审批中心。

## 4. 三条设计红线（防走回老路）

1. **凡是 agent 能自己做的，不给用户开关**
   ——开关是"我不信任 agent"的外化。信任机制应该是审批与预算，
   不是手动配置。每想加一个设置项，先问：这能不能是审批项？

2. **机制不出现在 UI**
   ——pack/tier/compact/charge 这些词不该出现在界面上。
   界面只有老板语言：进展、成本、风险、请示。

3. **每个页面必须回答"老板来这里做什么决定"**
   ——答不上来的页面就是仪表盘崇拜，砍。
   驾驶舱：今天需要什么审批？员工页：TA 编制要不要调？
   目标页：进度落后要不要加人？内核页：有没有异常进程要停？

## 5. 实施分期建议

| 期 | 内容 | 依据 |
|---|---|---|
| P1 | 驾驶舱 + 员工 + 审批中心（+统一审批队列 API） | 最小可感"公司"形态；审批 API 是唯一硬缺口 |
| P2 | 目标 O/KR + 知识聚合 + 活动 feed 投影 | Goal-driven 叙事成型 |
| P3 | B 类静默（cron/context/tools/skills 页面删除，能力转 agent 自治）+ settings 拆分 | 确认 agent 自治可靠后再砍 UI——先证明，后删除 |
| P4 | 成本中心 + 值班室 + 招聘向导 | 公司感收尾 |

**P3 的顺序纪律**：静默化必须放在最后——
先让 agent 在后台把这些事做好（可观测、可审计），
用户连续两周没打开过 cron 页，才证明可以删。
静默不是删除功能，是删除"需要人"的假设。
